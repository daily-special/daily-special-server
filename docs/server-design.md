# 서버 설계 — daily-special-server

> 서버가 무엇을 맡고 무엇을 안 맡는가, 그리고 어떤 순서로 만드는가.
> 이 문서는 자체 완결로 쓴다. 외부 문서를 참조하지 않는다.
> 최종 수정: 2026-08-06

---

## 0. 순서 — 클라가 요구하는 것을 보고 만든다

```
1단계  기동 확인 — bootRun + /actuator/health          ✅ 끝
3-a    오늘 상태 생성기 (허기·컨디션·기분·지갑)         ✅ 끝 — 순수 도메인
3-b    상태 → 우선 욕구                                 ← 규칙 미확정 (5절)
3-c    오늘 상태 조회 API                               ✅ 끝 — `docs/api.md`
2단계  플레이어 식별과 세이브 — 누구의 상태인가
3단계  나머지 하루 사이클 상태 — 소지금 · 재고 · 평판
4단계  관계와 공개된 취향 — 정보 공개 곡선의 저장소
5단계  클라 연동 · 배포
```

**2단계를 지금 시작하지 않는 이유가 이 문서에서 가장 중요하다.**

클라이언트는 아직 목 JSON을 화면에 띄우는 단계이고, 서버 없이 임시 상태를 **한 곳에 모아** 굴리기로 되어 있다. 그 임시 구현이 실제로 어떤 필드를 어떤 모양으로 쓰는지가 이 서버의 API 명세다. 그걸 보기 전에 엔티티를 설계하면 **두 번 만든다.**

**예선 제출물 중 서버에서 나오는 것은 없다.** 이 저장소의 목표 시점은 **본선(9/4~6)**이다. 예선 주간에 여기서 시간을 많이 쓰고 있다면 우선순위를 잘못 잡은 것이다.

그럼에도 3-a·3-c를 먼저 만든 것은 **순서가 값을 하기 때문이다.** 서버가 오늘 상태 생성기와 그 필드 모양을 먼저 정하고 클라에 알린 결과, 클라가 회신한 필드 목록이 이미 만들어둔 것과 정확히 맞아 **재작업이 0이었다.** 클라가 먼저 지어냈다면 둘 다 다시 만들었을 것이다.

## 1. 서버가 맡는 것

**플레이 중에 바뀌는 것 전부.**

| | 무엇 |
|---|---|
| **손님의 오늘 상태** | 허기·컨디션·기분·지갑. 매 방문 생성된다 |
| **오늘의 욕구 뽑기** | 손님이 오늘 무엇을 원하는가 |
| **관계** | 관계 수치, 단골 여부, **공개된 취향 정보** |
| **플레이어 자원** | 평판·소지금·재고 |
| **시장** | 그날의 시세 |

### 1-1. "결정적으로 생성된다"는 말의 뜻

손님의 오늘 상태는 무작위가 아니라 **씨앗에서 결정적으로** 나온다. 같은 세이브의 같은 날짜면 몇 번을 물어도 같은 값이어야 한다 — 안 그러면 클라가 재접속할 때마다 손님이 달라진다.

**씨앗 알고리즘** — 클라이언트가 C#으로 재현해야 하므로 언어 중립으로 잡았다.

```
text   = saveId + ":" + dayNumber + ":" + guestId
seed   = SHA-256(UTF-8(text))의 앞 8바이트, 빅엔디언 부호 있는 64비트
난수기  = SplitMix64(seed)
뽑는 순서 = 허기 → 컨디션 → 기분 → 지갑
```

`String.hashCode()`나 언어 기본 난수기를 쓰지 않는 이유가 여기 있다 — 언어마다 달라서 같은 손님이 서버와 클라에서 다르게 나온다. SHA-256과 SplitMix64는 상수까지 공개돼 있어 어디서든 같은 값을 낸다. **뽑는 순서와 열거 선언 순서도 명세의 일부다.**

### 1-2. 오늘 상태는 저장하지 않는다

생성이 순수하고 결정적이면 저장할 이유가 없다. **테이블 하나와 일관성 문제 하나가 통째로 사라진다.**

대가: 나중에 수치를 조정하면 과거 날짜의 상태도 같이 바뀐다. 지금은 지난 날을 되돌아보는 기능이 없어서 무해하다. 생기면 그때 스냅샷을 뜬다 — 기능이 요구할 때 붙이면 되는 일이지 미리 살 것이 아니다.

### 1-3. 이식 명세는 테스트다

만족도 엔진과 같은 방식이다. `VisitStateGeneratorTest`의 고정 벡터가 클라이언트 C# 구현의 명세다. 그 케이스를 옮겨 전부 통과시키면 두 구현이 어긋나지 않는다.

**여기 요약본을 만들지 않는다** — 두 벌이 되면 요약본이 뒤처지고, 그때 어느 쪽이 맞는지 알 수 없다.

## 2. 서버가 **안** 맡는 것

| 안 맡는 것 | 누가 |
|---|---|
| 고정 콘텐츠 (손님 페르소나·재료·요리·대사) | 파이프라인이 JSON으로 뱉고, **클라가 번들에 넣어 읽는다.** 서버를 거치지 않는다 |
| 화면·입력·연출 | 클라이언트 |
| 만족도 계산 | 지금은 클라이언트 (5절 참고) |

**고정 콘텐츠를 서버가 중계하지 않는 것이 의도다.** 클라가 오프라인에서도 뜨고, 콘텐츠가 바뀌면 앱 업데이트로 나간다.

### 2-1. 다만 "중계하지 않는다"는 "읽지 않는다"가 아니다

**이 구분을 흐리게 썼다가 실제로 오해를 샀다.** 클라 쪽에서 "서버가 페르소나를 중계하면 안 되는데 `prefers_affordable`은 어디서 얻느냐"는 질문이 왔다.

경계 기준은 3절 그대로다 — **플레이 중에 바뀌면 서버, 안 바뀌면 계약.** 선호 욕구는 안 바뀌니 계약이고, **서버가 계약을 읽는 것은 금지가 아니다.** 금지된 것은 그것을 클라에게 **배달하는** 일이다.

그래서 서버는 파이프라인 `guests.json` 스냅샷을 자기 리소스로 들고 `guest_id → prefers_affordable` 룩업만 만든다. 이름·소개·취향 구간은 읽지도 내보내지도 않는다.

**클라가 그 값을 요청에 실어 보내게 하지 않는다.** 그러면 클라가 스스로 부자 손님을 만들 수 있다.

대가는 **스냅샷이 한 벌 더 생기는 것**이다. 원본은 파이프라인이 갖고, 콘텐츠를 다시 뽑으면 서버 리소스와 클라 번들을 **같이** 갱신해야 한다. 어긋나면 `guest_id`가 안 맞아 전부 404가 된다 — 실제로 한 번 겪었고 `docs/api.md` 4절에 적어뒀다.

---

## 3. 경계를 가르는 한 문장

> **플레이 중에 바뀌면 서버, 안 바뀌면 파이프라인의 계약이다.**

애매한 것이 나오면 이 문장으로 자른다. 예를 들어 손님의 *취향 구간*은 안 바뀌니 계약이고, *그 취향이 플레이어에게 공개됐는지*는 바뀌니 서버다.

## 4. 스택과 그 이유

| | 고른 것 | 왜 |
|---|---|---|
| 언어 | Java 21 | LTS 중 지원이 가장 넓다. record·패턴 매칭·가상 스레드가 다 있다 |
| 프레임워크 | Spring Boot 4.1.0 | 현재 GA |
| 빌드 | Gradle (Kotlin DSL) | |
| DB | PostgreSQL 18 (Docker) | |
| 마이그레이션 | Flyway | 스키마 소유자를 한 곳으로 못박는다 |
| 테스트 | Testcontainers | |

### 4-1. H2를 쓰지 않는 이유

로컬은 H2, 배포는 Postgres로 두면 **문법 차이가 배포 시점에 터진다.** 마이그레이션 SQL을 두 방언에 맞춰 쓰는 비용도 계속 든다. Docker가 이미 있는 환경이라 진짜 Postgres를 쓰는 값이 싸다.

그 대가로 **테스트에 Docker가 필요하다.** GitHub Actions의 `ubuntu-latest`에는 Docker가 있어서 CI도 그대로 돈다.

### 4-2. Spring Security를 지금 넣지 않은 이유

넣는 순간 모든 엔드포인트가 기본 차단되고, 프로토타입 속도가 눈에 띄게 떨어진다. 플레이어 식별은 2단계에서 **가장 단순한 형태**로 먼저 넣고, 인증은 배포가 실제로 필요해질 때 붙인다.

### 4-3. Redis를 지금 넣지 않은 이유

지금 서버가 소유할 상태는 전부 영속이라 Postgres로 충분하다. 의존성만 얹으면 Boot가 기동 때 연결을 시도해서 **쓰지도 않는 컨테이너가 강제된다.**

**붙일 시점은 명확하다** — 비동기 멀티(단골이 남의 식당을 방문)나 세션 캐시가 들어올 때. 그때 `compose.yaml`에 5줄, 의존성 1줄이다.

## 5. 미정

- **플레이어 식별 방식** — 2단계에서 정한다. 프로토타입에선 인증 없는 식별자로 시작할 가능성이 높다
- **상태 → 우선 욕구 규칙** — 설계 문서에 예시 셋(`부상+피로→회복+순한`, `지갑 부족→저렴`, `축제 기분→특별+포만`)만 있고 규칙 전체가 없다. 게다가 "축제 기분"은 기분 3종(우울/평온/들뜸)에 없는 말이라 **들뜸을 가리키는지 별도의 날짜 이벤트 축인지 확인이 필요하다**
- **허기·가중치·저렴 성향 지갑 비율** — `VisitNumbers.defaults()`에 가정값으로 들어가 있다. 밸런스를 볼 때 가장 먼저 만질 자리다
- **만족도 엔진을 서버가 갖는가** — 지금은 클라이언트가 갖는다. 비동기 멀티를 붙일 때 다시 본다. **옮기게 되면 두 벌이 되지 않게 한쪽을 지운다**
- **배포 대상** — 미정
- **API 버저닝** — 클라 연동이 시작되면 정한다
